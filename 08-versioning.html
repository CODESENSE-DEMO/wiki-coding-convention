08. 버전 관리 규칙

규칙 VER-01 ~ VER-06최종 개정 2026-10-15

본 장은 사내 서비스·라이브러리(Union Framework 포함)의 버전 번호 체계, SNAPSHOT 사용, 릴리스·태그 절차, 의존성 버전 관리 기준을 정의한다. 브랜치·머지 규칙은 05장, 프레임워크 의존성 규칙은 06장 FW-01 과 함께 적용한다.

버전 번호

VER-01Semantic Versioning (MAJOR.MINOR.PATCH)

모든 아티팩트 버전은 MAJOR.MINOR.PATCH 세 자리 숫자로 표기한다. 두 자리(1.4)·날짜(20261015)·접미사(-final, -v2) 표기를 금지한다.

자리올리는 경우예
MAJOR하위 호환이 깨지는 변경 — REST API 필드 삭제·타입 변경, URI 변경, 프레임워크 공개 API·프로퍼티 키 삭제(VER-06)1.4.2 → 2.0.0
MINOR하위 호환을 유지하는 기능 추가 — 신규 API, 응답 필드 추가, 신규 ErrorCode1.4.2 → 1.5.0
PATCH동작 변경 없는 버그 수정·성능 개선·보안 패치1.4.2 → 1.4.3

상위 자리를 올리면 하위 자리는 0으로 초기화한다. 운영 배포 전 단계(POC·신규 서비스)는 0.y.z 를 사용하며, 이 기간에는 MINOR 증가로 호환성 변경을 허용한다. 첫 운영 배포 시 1.0.0 으로 시작한다.

VER-02커밋 type 과 버전 증가의 대응

릴리스 시 다음 버전은 직전 릴리스 이후 머지된 커밋(GIT-03)의 type 중 가장 큰 영향을 기준으로 정한다.

커밋버전 증가
본문에 BREAKING CHANGE: 가 포함된 커밋 (type 무관)MAJOR
featMINOR
fixPATCH
refactor · test · docs · chore단독으로는 릴리스 사유가 아니다. 다른 변경과 함께 릴리스되면 PATCH

하위 호환을 깨는 변경은 커밋 본문에 BREAKING CHANGE: 로 시작하는 문단을 두어 영향 범위와 마이그레이션 방법을 적어야 한다. squash merge(GIT-06) 시 이 문단이 누락되지 않도록 PR 본문에도 동일하게 기재한다.

좋은 예 
feat: 고객 조회 응답의 연락처 필드 구조 변경

BREAKING CHANGE: CustomerResponse.phone(String)을 contact.phone 으로 이동.
클라이언트는 contact 객체에서 값을 읽도록 수정해야 한다.

CUST-330

SNAPSHOT 과 릴리스

VER-03SNAPSHOT 사용 기준

  • develop·feature 브랜치의 pom.xml 버전은 항상 다음 릴리스 예정 버전 + -SNAPSHOT 으로 둔다. 예: 직전 릴리스가 1.4.0 이면 1.5.0-SNAPSHOT.
  • main·release·hotfix 브랜치의 버전에는 -SNAPSHOT 을 붙이지 않는다.
  • 운영(prod) 배포 아티팩트는 자신과 의존성 모두 SNAPSHOT 이 없어야 한다. SNAPSHOT 의존성이 남아 있으면 운영 배포를 금지한다.
  • SNAPSHOT 은 사내 Nexus snapshots 저장소, 릴리스 버전은 releases 저장소에만 배포한다. 같은 릴리스 버전을 재배포(덮어쓰기)하는 것을 금지한다 — 수정이 필요하면 PATCH 를 올린다.

VER-04릴리스 · 태그 절차

# 1. develop 에서 release 브랜치 생성 (GIT-01)
git switch -c release/1.5.0 develop

# 2. SNAPSHOT 제거 후 커밋
mvn versions:set -DnewVersion=1.5.0 -DgenerateBackupPoms=false
git commit -am "chore: 1.5.0 릴리스 버전 설정"

# 3. PR 로 main 에 merge commit 머지 (GIT-06) 후, main 의 머지 커밋에 태그
git tag -a v1.5.0 -m "release 1.5.0"
git push origin v1.5.0

# 4. develop 을 다음 SNAPSHOT 으로 올림
mvn versions:set -DnewVersion=1.6.0-SNAPSHOT -DgenerateBackupPoms=false
git commit -am "chore: 1.6.0-SNAPSHOT 개발 버전 설정"
  • 태그는 v{MAJOR}.{MINOR}.{PATCH} 형식의 annotated tag 로 main 의 머지 커밋에만 단다. 태그 이동·삭제 후 재생성을 금지한다.
  • hotfix 는 main 의 최신 태그에서 분기해 PATCH 만 올리고(1.5.0 → 1.5.1), 태그 후 develop 에도 반드시 백머지한다.
  • 릴리스 PR 본문에 직전 태그 이후 변경 목록(feat / fix / BREAKING CHANGE 구분)을 릴리스 노트로 작성한다. git log v1.4.0..release/1.5.0 --oneline 결과를 기준으로 정리한다.
나쁜 예 
git tag 1.5          # v 접두사 없음, 두 자리
git tag v1.5.0-final  # 접미사 사용
git tag -f v1.5.0     # 기존 태그 덮어쓰기

의존성 버전

VER-05의존성 버전 선언

  • Union Framework 버전은 union.version 프로퍼티 하나로만 관리한다(FW-01). 개별 모듈에 버전을 직접 적는 것을 금지한다.
  • Spring Boot parent 버전은 사용하는 Union Framework 가 빌드된 버전과 일치시킨다. 현재 기준: Union Framework 1.0.x ↔ Spring Boot 3.2.5.
  • Spring Boot BOM 이 관리하는 라이브러리는 버전을 명시하지 않는다. BOM 밖 라이브러리는 <properties> 에 {라이브러리}.version 으로 선언하고 ${...} 로 참조한다.
  • 버전 범위([1.0,2.0))·LATEST·RELEASE 지정을 금지한다. 빌드는 항상 재현 가능해야 한다.
좋은 예 
<properties>
    <java.version>17</java.version>
    <union.version>1.0.0</union.version>
    <jjwt.version>0.12.5</jjwt.version>
</properties>

VER-06호환성 보장 대상과 폐기(Deprecation) 절차

다음 항목의 삭제·이름 변경·의미 변경은 MAJOR 변경으로 취급한다.

구분호환성 보장 대상
서비스공개 REST API 의 URI, 요청/응답 필드명·타입, ErrorCode 값
Union FrameworkCOMMON_* 에러 코드, ApiResponse·PageResponse 필드, union.* 프로퍼티 키, 공개 클래스·메서드 시그니처
  1. 제거 대상은 먼저 MINOR 릴리스에서 @Deprecated(since = "1.5.0", forRemoval = true) 를 붙이고, Javadoc @deprecated 에 대체 수단을 적는다.
  2. 최소 한 번의 MINOR 릴리스 동안 기존 동작을 유지한 뒤, 다음 MAJOR 에서 제거한다.
  3. MAJOR 릴리스 시 해당 레포 wiki 개정 이력과 마이그레이션 가이드를 함께 배포한다.
참고 — 본 문서(위키) 자체의 버전(2.6 등)은 문서 개정 번호로, 위 아티팩트 버전 규칙과 별개로 MAJOR.MINOR 두 자리를 사용한다.
