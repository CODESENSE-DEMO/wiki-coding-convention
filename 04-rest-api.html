04. REST API 설계 규칙

규칙 API-01 ~ API-07최종 개정 2026-09-22

URI 설계

API-01URI는 자원 중심으로 설계한다

명사·복수형·kebab-case를 사용하고, URI에 동사를 넣는 것을 금지한다. 행위는 HTTP 메서드로 표현한다. 버전은 경로 첫 단에 둔다(/api/v1).

나쁜 예 
POST /api/v1/createReview
GET  /api/v1/getKbList?type=repo
좋은 예 
POST /api/v1/reviews
GET  /api/v1/shared-kbs?kind=repo_branch
GET  /api/v1/repos/{projectKey}/{repoSlug}/kb-config

API-02HTTP 메서드 의미를 지킨다

메서드용도비고
GET조회상태 변경 금지 (멱등)
POST생성, 비멱등 명령생성 성공 시 201 (@ResponseStatus(HttpStatus.CREATED))
PUT전체 교체멱등
PATCH부분 수정변경 필드만 전달
DELETE삭제성공 시 200 + envelope(data 없음). 204 는 사용하지 않는다

응답

API-03공통 응답 포맷

모든 응답은 Union Framework 의 ApiResponse envelope 를 사용한다. 필드명은 camelCase로 한다. 컨트롤러는 Response DTO 를 그대로 반환하고 프레임워크가 자동으로 감싼다. 컨트롤러에서 ApiResponse.ok(...) 나 ResponseEntity 로 직접 감싸는 것을 금지한다 (상태 코드가 필요하면 @ResponseStatus). 

// 성공
{
  "success": true,
  "code": "OK",
  "message": "성공",
  "data": { ... },
  "traceId": "8cb73d6623ac4770",
  "timestamp": "2026-09-22T09:25:47.403"
}

// 실패
{
  "success": false,
  "code": "CUSTOMER_001",
  "message": "고객을 찾을 수 없습니다. id=9999",
  "traceId": "8cb73d6623ac4770",
  "timestamp": "2026-09-22T09:25:47.403"
}

// 검증 실패 (400)
{
  "success": false,
  "code": "COMMON_400",
  "message": "잘못된 입력값입니다.",
  "errors": [ { "field": "email", "rejectedValue": "bad", "reason": "이메일 형식이 올바르지 않습니다." } ],
  "traceId": "...", "timestamp": "..."
}
나쁜 예 
@GetMapping("/{id}")
public ResponseEntity<CustomerResponse> get(@PathVariable Long id) {
    return ResponseEntity.ok(customerService.getCustomer(id));
}
좋은 예 
@GetMapping("/{id}")
public CustomerResponse get(@PathVariable Long id) {
    return customerService.getCustomer(id);      // 프레임워크가 ApiResponse 로 래핑
}

API-04상태 코드 기준

코드사용 기준
200 / 201조회·수정·삭제 성공 / 생성 성공. 항상 envelope 를 내려보내므로 204 는 쓰지 않는다
400요청 형식·검증 오류 — 프레임워크가 COMMON_400 으로 자동 변환
401 / 403미인증(COMMON_401) / 권한 없음(COMMON_403) — 프레임워크 보안 계층이 처리
404자원 없음 — EntityNotFoundException 계열 (status 404 ErrorCode)
409상태 충돌 (중복 등록, 동시 수정 등) — status 409 ErrorCode 의 BusinessException
500서버 내부 오류(COMMON_500) — 비즈니스 예외를 500으로 뭉개는 것을 금지한다

API-05페이징 표준

목록 API는 page(0-base)·size(기본 20, 최대 100) 쿼리 파라미터를 받고, 프레임워크 PageResponse 로 응답한다. 컨트롤러는 @PageableDefault(size = 20) Pageable 로 받고, Service 는 PageResponses.from(page).map(Response::from) 으로 변환한다. Spring Data Page 를 그대로 반환하는 것을 금지한다. 

GET /api/v1/customers?page=0&size=20&sort=createdAt,desc

"data": {
  "content": [ ... ],
  "page": 0,
  "size": 20,
  "totalElements": 142,
  "totalPages": 8,
  "first": true,
  "last": false
}

요청 처리

API-06요청 검증은 진입 지점에서 수행한다

Bean Validation(@Valid, @NotNull, @Size 등)을 Request DTO에 선언하고, 검증 실패는 프레임워크 전역 핸들러가 400 + errors[] 로 일괄 변환한다. @RequestBody 에 @Valid 를 빠뜨리면 검증이 전혀 수행되지 않으므로 리뷰 시 반드시 확인한다. Service 본문에서 형식 검증을 반복하는 것을 금지한다.

API-07호환성 유지

배포된 API의 필드 삭제·의미 변경은 breaking change로 간주한다. 필드 추가는 허용한다. breaking change가 필요하면 신규 버전(/api/v2)을 추가하고 구버전은 최소 1개 분기 유예 후 제거한다.

참고 — 신규 API는 머지 전 OpenAPI(Swagger) 문서화가 완료되어야 하며, PR 본문에 해당 엔드포인트 스펙 링크를 첨부한다.
