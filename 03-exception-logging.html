예외 처리

EX-01비즈니스 예외 체계

비즈니스 예외는 Union Framework 의 BusinessException(규칙 위반) 또는 EntityNotFoundException(조회 대상 없음)을 상속한다. 에러 코드는 도메인별로 io.union.core.error.ErrorCode 를 구현한 enum ({도메인}ErrorCode)으로 중앙 관리하며, 코드 문자열은 {도메인}_{3자리 숫자} 형식으로 한다 (예: CUSTOMER_001, CONSENT_002). HTTP 상태 코드는 ErrorCode 의 status 에 함께 정의한다. COMMON_* 는 프레임워크 예약 코드이므로 애플리케이션에서 재정의하지 않는다. 

public enum CustomerErrorCode implements ErrorCode {
    CUSTOMER_NOT_FOUND("CUSTOMER_001", "고객을 찾을 수 없습니다.", 404),
    CUSTOMER_ALREADY_WITHDRAWN("CUSTOMER_002", "이미 탈회된 고객입니다.", 409);
    // code / message / status 필드와 getter
}

public class CustomerNotFoundException extends EntityNotFoundException {
    public CustomerNotFoundException(Long id) {
        super(CustomerErrorCode.CUSTOMER_NOT_FOUND, "고객을 찾을 수 없습니다. id=" + id);
    }
}

단순 조건 검증은 예외 클래스를 만들지 않고 Assert 유틸을 사용한다. 도메인 규칙 위반에 IllegalStateException·IllegalArgumentException 을 던지는 것을 금지한다 — 전역 핸들러가 원인을 알 수 없는 500(COMMON_500)으로 처리한다.

나쁜 예 
if (status == CustomerStatus.WITHDRAWN) {
    throw new IllegalStateException("이미 탈회된 고객입니다.");   // → 500
}
좋은 예 
Assert.isTrue(status != CustomerStatus.WITHDRAWN, CustomerErrorCode.CUSTOMER_ALREADY_WITHDRAWN);  // → 409
Assert.notNull(tier, "등급은 필수입니다.");                                                          // → 400 COMMON_400

EX-02예외 삼킴 금지

catch 블록을 비워 두거나, 로그만 남기고 정상 흐름처럼 계속 진행하는 것을 금지한다.

나쁜 예 
try {
    bitbucketClient.postComment(prId, comment);
} catch (Exception e) {
    // 무시
}
좋은 예 
try {
    bitbucketClient.postComment(prId, comment);
} catch (BitbucketApiException e) {
    log.error("PR 코멘트 게시 실패. prId={}", prId, e);
    throw new CommentPublishException(prId, e);
}

EX-03예외 처리는 전역 핸들러로 모은다

HTTP 응답 변환은 프레임워크의 GlobalExceptionHandler 가 수행한다 (프레임워크 가이드 03 매핑표 참고). Controller·Service에서 try-catch로 에러 응답을 직접 만드는 것을 금지한다. 애플리케이션에서 @RestControllerAdvice 를 새로 정의하는 것도 금지한다 — 프레임워크 핸들러가 통째로 비활성화되어 응답 포맷이 깨진다. 공통 처리가 더 필요하면 개발본부에 프레임워크 반영을 요청한다.

EX-04원인 예외를 보존한다

예외를 변환해 다시 던질 때는 반드시 원인 예외(cause)를 함께 전달한다. 스택트레이스 유실을 금지한다.

EX-05Exception / Throwable을 직접 catch하지 않는다

구체적인 예외 타입을 catch한다. 최후 방어선이 필요한 경우는 전역 핸들러와 Celery task 최상위로 한정한다.

EX-06제어 흐름에 예외를 사용하지 않는다

"없을 수 있는" 정상 상황은 Optional·boolean 반환으로 표현하고, 예외는 비정상 상황에만 사용한다.

로깅

LOG-01로그 레벨 기준

레벨기준예
ERROR즉시 확인이 필요한 실패. 알림 대상.vLLM 호출 실패로 리뷰 미게시
WARN처리는 계속되나 비정상 신호.fallback 경로로 KB 결정, 재시도 발생
INFO운영상 의미 있는 상태 변화.KB 인덱싱 시작/완료, 정책 변경
DEBUG개발/장애 분석용 상세 흐름. 운영 기본 출력 제외.컨텍스트 빌드 중간 산출물 크기

LOG-02플레이스홀더 바인딩을 사용한다

문자열 연결(+)로 로그 메시지를 만드는 것을 금지한다.

나쁜 예 
log.info("리뷰 시작: " + prId + ", repo: " + repoSlug);
좋은 예 
log.info("리뷰 시작. prId={}, repoSlug={}", prId, repoSlug);

LOG-03로그에는 식별자를 포함한다

추적 가능하도록 관련 식별자(customerId, prId, projectId 등)를 key=value 형식으로 포함한다. "실패했습니다"처럼 식별자 없는 로그를 금지한다. 요청 추적 ID(traceId)는 프레임워크가 MDC 에 넣어 주므로 로그 패턴에 [%X{traceId:-}] 를 포함하고, 메시지 본문에 직접 쓰지 않는다.

LOG-04System.out.println / printStackTrace 금지

모든 출력은 SLF4J 로거를 통한다. Python은 print 대신 logging 모듈을 사용한다.

LOG-05민감정보 마스킹

다음 항목은 로그에 평문 기록을 금지한다: 액세스 토큰·비밀키, 비밀번호, 주민등록번호, 계좌·카드번호, 고객 개인정보(이름·연락처·이메일 전체). 부분 확인이 필요한 경우 마스킹하여 기록한다 (예: token=xoxb-****, email=k***@unionplace.co.kr). 소스 코드·로그·예외 메시지에 시크릿이 포함되는 것은 보안 사고로 간주한다.
